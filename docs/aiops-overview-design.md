# ManageOne 告警 AI 端到端处理架构设计

针对 ManageOne 云管平台的运维场景，引入大模型（LLM）和 AI Agent 可以将传统的「人找告警」转变为「AI 处理告警」。这是一个典型的 AIOps（智能运维）端到端解决方案。

---

## 1. 告警分类体系设计

在 ManageOne 环境中，告警首先需要被标准化和分类，以便 AI 能够准确识别其上下文。完整的云管平台告警通常分为以下七大类：

| # | 类别 | 说明 | 示例 |
|---|------|------|------|
| 1 | 容量类 (Capacity) | 资源容量不足 | 磁盘空间满、内存使用率超 90%、VPC IP 地址池耗尽 |
| 2 | 阈值/性能类 (Performance) | 性能指标超限 | CPU 持续飙高、网络时延大、存储 IOPS 达到瓶颈 |
| 3 | 证书/安全类 (Security) | 安全风险 | SSL 证书即将过期、AK/SK 泄露、异常登录失败 |
| 4 | 硬件/底座故障类 (Hardware) | 物理设备故障 | 物理机宕机、硬盘坏道/亮红灯、交换机端口 Down |
| 5 | 网络连接类 (Network) | 网络链路异常 | 专线中断、BGP 邻居断开、南北向网络不通 |
| 6 | 服务/应用状态类 (Service) | 微服务/应用异常 | ManageOne 自身微服务（如 Nova、Cinder 控制面）异常退出、数据库主备切换 |
| 7 | 配置合规类 (Compliance) | 配置不合规 | 资源创建未打标签、安全组规则配置过于开放（如 0.0.0.0/0） |

## 2. 告警聚合处理（降噪过滤）

云环境一旦发生底层故障（如宿主机宕机），会瞬间引发数百个虚拟机和应用的告警（告警风暴）。AI 和算法介入后的聚合分为三步：

### 2.1 时间与频次聚合
针对同一资源在短时间内的反复告警（如网络抖动引起的频繁 Down/Up），进行静默和去重，只保留一条有效告警。

### 2.2 拓扑/血缘聚合
结合 ManageOne CMDB 的资源拓扑树。如果「物理交换机 Down」，AI 会自动将该交换机下挂的所有「物理机网络中断」「虚拟机离线」「应用无法访问」告警聚合为一个父子事件 (Incident)，根因指向交换机。

### 2.3 语义与时序关联（AI 模式挖掘）
利用自然语言处理 (NLP) 分析告警文本描述，将时序上经常一起出现、语义高度相关的未知告警进行动态聚类。

---

## 3. AI Agent 自动修复与处理建议

这是端到端流程的核心，AI Agent 将根据聚合后的事件类型，决定是「自动执行操作」还是「提供人类建议」。

### A. AI Agent 自动修复流程（闭环）

对于标准化、风险低且有明确 SOP（标准作业程序）的告警，AI Agent 直接调用 ManageOne API 或自动化工具（如 Ansible/运维脚本）进行闭环。

| 告警类型 | 自动修复动作 |
|----------|-------------|
| 容量类-磁盘满 | Agent 自动执行脚本清理临时文件/旧日志，或调用 API 自动扩容云盘 20% |
| 证书过期类 | Agent 提前 30 天拦截告警，自动调用 KMS 或证书管理 API 签发新证书，并推送到相应的 LB（负载均衡）或网关 |
| 服务状态类-进程僵死 | Agent 自动执行平滑重启指令，并进行拨测，验证成功后自动在系统内将告警标记为「已处理」 |

### B. 无法自动修复的告警（辅助决策 / Copilot）

对于高风险（如硬件更换）或未知故障，AI Agent 转化为「专家助手」，利用 RAG（检索增强生成）技术：

- **根因分析 (RCA)**：分析聚合后的日志和指标，指出「可能是由于 03:00 的系统补丁更新导致内存泄漏」
- **知识库检索**：自动搜索 ManageOne 产品文档、历史相似工单、已知 Bug 库
- **输出处置建议**：生成分步操作指南（例如：「1. 登录主机检查 dmesg 日志；2. 若确认内存条硬件故障，请联系供应商派单更换，备件号 XXX」）

## 4. 用 AI 简化配置流程（意图驱动运维）

传统的告警规则配置需要运维人员在界面上繁琐地选择资源树、指标、设定数字阈值。引入 AI 后：

### 自然语言生成配置
运维人员只需在对话框输入：「帮我监控所有生产环境的 MySQL 数据库，如果 CPU 超过 80% 持续 5 分钟，就发微信给 DBA 团队。」AI Agent 会自动将这句话解析为 JSON 配置，并在 ManageOne 中生成相应的告警策略和通知规则供用户确认。

### 动态阈值自适应配置
抛弃静态数字配置。AI 根据资源过去 30 天的历史数据，自动画出「正常基线」。当指标偏离该基线时（例如某台平时 CPU 只有 10% 的机器突然飙到 50%），AI 自动生成异常事件，无需人工提前预设 50% 这个数字。

## 5. 概览页面布局设计

概览页面的核心目的是向 IT 管理者展示 AI 的 ROI（投资回报率）和当前的系统健康度。建议采用以下模块化布局：

| 模块 | 展示形式 | 数据维度 & 业务含义 |
|------|---------|-------------------|
| 1. 告警自动处理成果 | 核心数字卡片 (Hero Metric) | 「AI 自动闭环数：3,452 次」展示近 30 天内 AI Agent 成功执行修复的告警数量。可附加换算指标：「节省人工时：约 280 小时」，直观体现 AI 价值 |
| 2. 告警降噪与聚合率 | 漏斗图 / 对比进度条 | 原始告警：100,000 → 聚合后事件：8,500（降噪率 91.5%）。展示系统拦截了多少无用或重复的告警风暴，减轻了多少运维噪音 |
| 3. 告警总数与级别分布 | 环形图 (Donut Chart) + 计数 | 展示当前未处理告警总数。按颜色区分：致命 (Critical, 红色)、严重 (Major, 橙色)、一般 (Minor, 黄色)、提示 (Info, 蓝色) |
| 4. TopN 告警类型 | 横向柱状图 (Bar Chart) | 展示最频发的告警类别。例如：1. 容量类 (45%)；2. 阈值类 (30%)；3. 硬件类 (15%) 等。指导下一步的基础设施优化方向 |
| 5. 处理趋势与人机对比 | 双线面积图 (Area Chart) | 横轴为时间（天/周）。一条线展示「AI 自动处理趋势」，另一条线展示「人工闭环趋势」。理想的图表走向应当是 AI 处理的线条逐渐攀升并占据主导，人工处理的线条逐渐下降或保持平稳（只处理复杂疑难杂症） |
